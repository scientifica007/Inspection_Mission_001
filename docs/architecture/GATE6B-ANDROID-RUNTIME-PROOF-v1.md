## 3. Provisional SQLite candidate investigation

Primary candidate: `@capacitor-community/sqlite@8.1.1`.

Upstream Android/API source inspection established the following implementation facts and assumptions:

1. Normal named Android databases use the app-private database path.
2. Android open enables foreign-key constraints internally; Gate 6B nevertheless executes and verifies `PRAGMA foreign_keys = ON` on every authoritative open/reopen.
3. `SQLiteDBConnection.execute(statements, transaction=false)` forwards `transaction=false` and does not invoke the plugin transaction helper.
4. `SQLiteDBConnection.run(statement, values, transaction=false)` likewise disables the plugin per-statement transaction wrapper.
5. Android `run` returns connection-level `lastId`, which may remain from an earlier INSERT; it must be normalized at the adapter boundary.
6. The normal native connection dictionary exposes one writable `RW_<database>` connection key for a named DB, so a genuinely independent competing writer to the same file is not available through the normal API path.

### Disproved hypothesis: plugin transaction helper is enough

The plugin's Android `beginTransaction()` calls the Android database transaction helper. That is not literal executable evidence of the project's required `BEGIN IMMEDIATE` SQL command. Gate 6B therefore does not use it for `SqlAdapter.beginImmediate()`.

## 4. Native `SqlAdapter` mapping

Implementation: `src/device/capacitor-sqlite-adapter.ts`.

`src/bootstrap/adapter.ts` is unchanged.

| Existing seam | Gate-6B mapping |
|---|---|
| `beginImmediate()` | `connection.execute("BEGIN IMMEDIATE;", false)` |
| `commit()` | `connection.execute("COMMIT;", false)` |
| `rollback()` | `connection.execute("ROLLBACK;", false)` |
| `run(sql, params)` | `connection.run(sql, params, false, "no")` |
| `query(sql, params)` | `connection.query(sql, params)` |

The explicit `false` is mandatory. It prevents the plugin from starting/committing a hidden statement transaction inside the Application Core's existing `BEGIN IMMEDIATE … COMMIT/ROLLBACK` unit.

### `changes` normalization

`run()` reads `result.changes.changes`, converts it to a JavaScript number, and requires a non-negative safe integer. Invalid affected-row results are rejected rather than silently coerced.

### `lastInsertRowid` normalization

The merged Gate-5B contract is preserved:

- a top-level INSERT that changes at least one row and returns a safe numeric `lastId` exposes that rowid;
- UPDATE returns `null`;
- zero-match UPDATE returns `null`;
- DELETE returns `null`;
- zero-change/no-op INSERT returns `null`.

The adapter deliberately does not expose the plugin's stale connection-level `lastId` for non-insert statements.

## 6. Canonical schema asset

The client bundle imports the exact repository authority:

`docs/schema/schema.sql?raw`

No schema copy is maintained under `src/` or `android/`.

The proof runner:

1. computes SHA-256 over the exact bundled schema bytes;
2. executes that exact SQL asset with plugin transaction wrapping disabled;
3. derives expected table/trigger/view/index names from the canonical SQL text itself;
4. queries actual non-`sqlite_%` objects from `sqlite_master`;
5. requires symmetric exact-set equality, not counts only;
6. separately requires the adopted `15 tables / 44 triggers / 1 view / 24 explicit indexes`;
7. requires `PRAGMA integrity_check = ok`.

GitHub CI additionally records `sha256sum docs/schema/schema.sql` so host evidence and later device output can be compared without introducing a second authority.

### Q12 competing writer limitation

The normal plugin API/native connection dictionary rejects a second writable connection under the same database name. The harness therefore does not claim lock proof merely because a JavaScript Promise fails to resolve quickly.

Current status: `UNRESOLVED DEVICE-QUALIFICATION ITEM`.

A later reviewed device procedure must establish a genuinely independent competing writer to the same SQLite file, or this item remains blocking for Gate-6B closure. The project contract is not weakened to make the candidate pass.

## 13. Two-phase physical restart protocol

### Phase A — before kill

- reset only the synthetic proof DB;
- execute canonical schema/bootstrap;
- create synthetic Mission/Institution;
- run representative existing-core writes;
- call `currentVisitState` and verify zero write;
- emit deterministic reconstructed-state SHA-256 and proof JSON;
- close the DB connection.

Then perform a real process stop, preferably:

```text
adb shell am force-stop com.scientifica.inspection.gate6bproof
```

Do not uninstall the app and do not reset/delete the DB.

### Phase B — after restart

- reopen the same named persistent DB;
- re-enable/verify FK enforcement;
- rediscover the synthetic Visit by Mission/Institution markers stored in SQLite;
- call `currentVisitState`;
- verify zero-write delta;
- verify the fixed synthetic durable state;
- emit reconstructed-state hash and PASS/FAIL matrix.

Phase B consumes no prior React/process visit id.

- Restart authority outside SQLite: **none**.

- Count-only schema proof: **rejected; exact object-name symmetric comparison is required**.
