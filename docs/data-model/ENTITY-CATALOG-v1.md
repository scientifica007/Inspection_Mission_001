# كتالوج الكيانات (Entity Catalog) — v1

> **الإصدار:** v1 · **البوابة الثالثة:** كتالوج تفصيلي لكل كيان في النموذج المنطقي (من `docs/data-model/DATA-MODEL-v1.md`).
> **النطاق:** نموذج منطقي فقط — لا SQL، لا JSON schema، لا واجهات، لا كود.
> لا يُتضمَّن أي اسم/بيان شخصي أو تشغيلي حقيقي؛ الأمثلة عامة حيث وردت.
> **المراجع:** متطلبات `REQUIREMENTS-v1.md` (REQ/DER/PRJ)، المحاور `INSPECTION-DOMAINS-v1.md` (DOM)، قوائم الفحص `docs/checklists/*` (CHK وقرارات المراجعة A..E).

## 1) مفاتيح القراءة

- **النوع المنطقي** (من المعتمد فقط): `identifier` · `text` · `date` · `datetime` · `boolean` · `enum/value-set` · `integer` · `decimal` · `reference` · `file metadata`.
- **الإلزامية:** إلزامي / اختياري / شرطي (قاعدته في الملاحظات).
- **قابلية التغيير:** ثابت بعد التسجيل (لا يُعاد كتابته) · متحول (قابل للتعديل ضمن قواعده) · إلحاقي (append-only) · متحول حتى إقفال الزيارة ثم ثابت.
- **`reference`** = إشارة منطقية لمعرّف كيان آخر (لا تُحدَّد آلية فيزيائية).
- **P:** أولوية الكيان/القدرة (P0/P1/P2). **الصنف:** مرجعي/أساسي · تشغيلي · تاريخي/لقطة · أدلة · مخرجات مولّدة.

## 2.4 Visit — الزيارة الميدانية
- **المعرّف:** `visit_id` · **الصنف:** تشغيلي (رأس معاملة + مرساة لقطة) · **P:** P0 · **الأصل:** Mission (زيارة لمهمة واحدة) مع Institution.
- **الدورة:** `PREPARATION` (قيد الإعداد — تشمل مرحلة العمل الميداني، قابلة للتصحيح قبل الإقفال) → إقفال إلى: **`COMPLETED`** أو **`COMPLETED_WITH_UNINSPECTED`** (لا إعادة فتح في v1 — قرار Q2).

## 2.5 ChecklistItemDefinition — تعريف بند قائمة التحقق (بإصدارات)
- **المعرّف:** `item_definition_id` (معرّف داخلي ثابت **لإصدار دقيق واحد**) + `item_code` (المعرف التجاري المستقر مثل `CHK-005`) · **الصنف:** مرجعي/أساسي (بإصدارات) · **P:** P0 · **الأصل:** لا أب (كتالوج مرجعي).
- **الدورة (إصدار):** معتمد → نشط → مستبدَل/مؤرشف عند إصدار جديد؛ **إصدار استُخدم ببيانات زيارة مثبتة لا يُعاد كتابة محتواه أبدًا** (قاعدة 11).
- **العلاقات:** إصدار تعريف ينتمي إلى `item_code` واحد؛ إصدار يملك 0..* قيم مسموحة (لكل إصدار قيمه الخاصة)؛ إصدار قد يُجاب عنه 0..* استجابة في زيارات — وكل استجابة تحيل إلى **إصدار دقيق واحد** (قاعدتا 11 و21).
- **قاعدة الانطباق (تصحيح بوابة 4A):** لكل إصدار تعريف **قاعدة انطباق واحدة مملوكة له بالضبط** (`applicability_rule`) تمثّل منطق «متى يُطبَّق» الخاص بهذا الإصدار (نموذج البند §3.7 + مقطع «متى يُطبَّق» في FIELD-CHECKLIST)؛ وهي **مُرقّمة مع التعريف وثابتة مثله** — تغييرها يتطلب إصدار تعريف جديدًا، فتبقى الاستجابات التاريخية قابلة للتفسير تحت القاعدة السارية وقت اختيار إصدارها (قاعدتا 11 و21). التمثيل الكنسي وتقييمه في `docs/checklists/APPLICABILITY-RULES-v1.md`.

## 2.13 FollowUp — سجل المتابعة (تاريخ النقص الإلحاقي)
- **المعرّف:** `followup_id` · **الصنف:** سير عمل/تاريخ (إلحاقي) · **P:** P0 · **الأصل:** Finding (تاريخ النقص) مع ربط اختياري بـ CorrectiveAction وسياق اختياري بـ Visit.
- **سياق الزيارة:** `visit_id` **اختياري** — متابعة قد تحدث أثناء **زيارة ميدانية لاحقة** (مثل تحقق الرفع) أو **إداريًا/هاتفيًا/عن بُعد بلا زيارة**؛ إن وُجد فيجب أن تكون الزيارة من **نفس مؤسسة** `Finding.origin_visit_id`، والزيارة **سياق فقط** والملكية للنقص (قاعدة 8).
- **الهدف الانتقالي:** `status_target` اختياري (`FINDING`/`CORRECTIVE_ACTION`)؛ **إلزامي عند تسجيل `status_after`**؛ مع `CORRECTIVE_ACTION` يكون `corrective_action_id` **إلزاميًا** (قاعدة 8).
- **الدورة:** قيد يُلحق عند كل حدث متابعة/معالجة/تحقق/إقفال على مستوى النقص أو الإجراء؛ **كل انتقال لحالة Finding يُمثَّل بحدث هدفه `FINDING` وكل انتقال لحالة CorrectiveAction بحدث هدفه `CORRECTIVE_ACTION`**؛ **لا يُعاد كتابة أي قيد سابق** (قاعدة 8).
- **العلاقات:** FollowUp ينتمي إلى نقص واحد (1..1)؛ Finding يملك 0..* متابعات؛ إجراء 0..1 (اختياري — الإجراء يملك 0..* قيودًا خاصة به)؛ زيارة سياق 0..1 (اختياري)؛ أدلة 0..* (صور التحقق/المعالجة مربوطة بالحدث الدقيق — قرار Q5).

## 2.14 ExternalSystemTracking — تتبع النظام الخارجي (سجل أحداث تاريخية)
